How the harness works

Models do the reading.
Code keeps it grounded.

The harness wraps page preparation, model calls, validation, retries and assembly into a resumable workflow. Every page result is cached so a run can continue after a usage limit or interruption.

01 / INPUT

Render & inspect

PyMuPDF renders pages. Text layers become spelling hints; scans are handled as images.

02 / FIGURES

Mark candidates

Local OpenCV detects likely diagrams. Candidates get stable labels the model can refer to.

03 / EXTRACT

Constrained reading

Claude CLI and Codex CLI return page data against a strict JSON schema.

04 / CHECK

Validate & verify

Pydantic validates output. Optional verification rechecks doubtful pages with either engine.

05 / ASSEMBLE

Link & package

Continuation pages and solutions are linked; figures are cropped and anomalies flagged.

Coordinates are resolved by local image code; the model selects figure labels or suggests rough regions for local refinement.

What made this hard

PDFs are pages, not records.

Question books mix typography, scans, formulas, diagrams and inconsistent numbering. The harness is designed around those messy edges.

CHALLENGE 01

Figures have no clean boundaries

A diagram may be split into lines, labels and shapes—or sit beside equations and page furniture.

Approach: detect broad candidates locally, label them on the page, then ask the model which belong to each question.
CHALLENGE 02

Layout shifts from book to book

Questions can span pages, while solution sections reuse numbers across chapters.

Approach: keep page-level results, merge continuations and link each solution to the nearest earlier matching question.
CHALLENGE 03

Long runs are easy to interrupt

Subscription usage limits, rate limits and model variation make all-at-once processing brittle.

Approach: cache each page, retry and park unavailable engines, resume runs, and flag uncertain output for review.
Why it helps an internal team

Turn a one-off scan into reusable knowledge.

Use pyq·forge as a practical first pass for digitising internal question banks. People keep control of the source material and can review the extracted result before it enters another workflow.

01

Build searchable question sets

Collect question text, options, answers, years and chapter metadata in a consistent JSON format.

02

Keep diagrams attached

Store useful figure crops alongside their questions instead of losing context in a plain text export.

03

Review with evidence

Use the local UI to inspect questions against original page scans, focus on flags and repair source-page results.

04

Share a repeatable process

Run pilots consistently, compare engine outputs, resume interrupted work and preserve a report for each run.

Start with a small pilot

One chapter is enough to learn.

Install the project, sign in to the CLI you already use, inspect a short range, then run extraction and review the result locally. Keep API keys unset; pyq·forge uses the CLI subscription login.

Python 3.10+Claude CLI and/or Codex CLILocal workspace

For internal use, agree on source-PDF handling and review expectations before processing a shared collection. Subscription logins are intended for the subscriber’s own use.

# Install
uv venv .venv
uv pip install --python .venv/bin/python -e ".[dev]"

# Sign in to one or both supported CLIs
claude       # then /login
codex login

# Check setup, then preview figure detection
.venv/bin/python -m pyqforge doctor
.venv/bin/python -m pyqforge inspect book.pdf --pages 20-28

# Extract and review locally
.venv/bin/python -m pyqforge extract book.pdf --out out \\
  --pages 20-28 --engine auto --verify
.venv/bin/python -m pyqforge ui

Try it on one representative chapter.

Measure what it gets right, inspect what it flags, then decide where the workflow fits your team.
